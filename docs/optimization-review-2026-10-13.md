**3. 資料保存與設定恢復**

**3.1 修正儲存失敗後的狀態一致性（P1）**

[ShellViewModel.cs](D:/Codex/Secondary/src/Secondary.App/ShellViewModel.cs:56) 的 SaveRuntime 先更新 Settings，再呼叫 store.Save。下次相同設定會因 next == Settings 而直接返回；[SettingsStore.cs](D:/Codex/Secondary/src/Secondary.Core/SettingsStore.cs:57) 在儲存失敗時也沒有設定待重試狀態。

重現：讓設定父路徑被測試檔案占用 → 切換 Dark → 保存失敗，但記憶體 Theme 已是 Dark → 修復路徑 → 再保存 Dark → settings.json 仍不存在。

建議保存「已持久化快照」與「目前套用狀態」，或者維持明確的 dirty 狀態。儲存失敗後顯示可操作的重試入口，成功才清除待保存狀態。顯示器、主題、快捷鍵、採樣及導航偏好應採一致策略。

驗收：模擬路徑失效、磁碟寫入失敗或暫時鎖定；修復後重試相同值，磁碟資料及重啟結果均正確。

**3.2 避免多實例覆蓋（P1）**

[App.xaml.cs](D:/Codex/Secondary/src/Secondary.App/App.xaml.cs:12) 未建立單實例協調；每個視窗持有自己的整份 Settings 快照，寫入時整份覆蓋。

重現：兩個模型先讀取同一空設定；A 保存便箋組件；B 保存主題；重新讀取後組件數量變成 0。原子替換只能避免寫入一半的檔案，無法避免舊快照覆蓋新資料。

建議預設採單實例，第二次啟動顯示原視窗。如需要不同副屏各跑一份，改用獨立設定檔／明確 profile，並加入檔案版本衝突檢查。

驗收：重複啟動只存在一個寫入者；或兩個 profile 的組件及快捷設定完全獨立。

**3.3 統一快捷資料大小上限（P2）**

[ShortcutLibrary.cs](D:/Codex/Secondary/src/Secondary.Core/ShortcutLibrary.cs:69) 讀取拒絕超過 4,000,000 bytes；Save 只檢查筆數與欄位，沒有檢查序列化後的總大小。

重現：60 個捷徑、各 20 步、每步 4,096 字的合法啟動參數，Save 回傳成功；檔案為 5,233,791 bytes；再次 Load 回傳 0 筆、ReadOnly=true，訊息為「捷徑資料過大」。原檔仍保留，但應用程式無法載入自己保存的內容。

建議在替換原檔前檢查 UTF-8 序列化位元組大小，並與讀取共用同一常數。超限時保留目前可讀檔案，顯示需要縮減的內容或大小。settings.json 也應加入合理的總大小與 JSON 深度限制，避免讀取異常大檔案。

驗收：大小臨界值、中文字與跳脫字元都能穩定往返；保存成功的資料一定能重新載入。

**3.4 恢復、備份與草稿（P2）**

目前損壞設定會保留原檔並在下次保存前備份，快捷資料損壞則進入唯讀，這些保護值得保留。可增加「匯出」「選擇備份恢復」「開啟資料位置」及內容摘要，讓使用者能自行恢復。

便箋使用手動保存。建議增加草稿保存或清楚的未保存指示；要保留完整設定前版本，再決定覆寫策略。待辦、計數器等操作則可用序列化的保存佇列，維持 UI 回應並防止寫入順序逆轉。

驗收：異常退出後已保存內容可讀；備份恢復包含預覽；保存失敗時編輯內容仍可繼續修正。

**4. 監測正確性、資料來源與程序生命週期**

**4.1 改善交換鏈選擇與新鮮度（P1）**

[FrameWindow.cs](D:/Codex/Secondary/src/Secondary.Core/FrameWindow.cs:26) 以最近 60 秒事件最多的鏈作為主鏈；[GameTelemetrySession.cs](D:/Codex/Secondary/src/Secondary.App/Monitoring/GameTelemetrySession.cs:25) 則用任何鏈最近收到事件的時間判斷整體資料是否新鮮。

重現：old 鏈先產生 1,000 幀，new 鏈之後以 100 FPS 持續產生 210 幀。Read 仍選 old，FPS=null，1% Low=1000；new 鏈確實有新的有效幀。這會出現在交換鏈重建、切換場景或呈現方式改變的情境。

建議先排除近期已無活動的鏈，再用事件密度及短期穩定性選擇主鏈；設切換遲滯以免多鏈抖動。新鮮度應屬於「選定鏈」，鏈切換時重設其統計與曲線。可提供進階鏈選擇，但一般介面以可理解的狀態為主。

驗收：舊鏈停止、新鏈持續時能在定義的短時間內切換；不延用舊鏈的 1% Low；同時多鏈與亂序事件仍不混算。

**4.2 建立成功的 PresentMon 實機驗收（P1）**

現有指定 PID＋開始時間、固定官方二進位雜湊、唯一 ETW session、表頭解析、無資料顯示「—」的設計應保留。已核對官方固定 tag 的 v2 CSV 欄位包含 FrameTime、CPUBusy、CPUWait，現行主要解析路徑並非單純套用錯誤舊欄位。[PresentMon v2.6.0 原始碼](https://github.com/GameTechDev/PresentMon/blob/v2.6.0/PresentMon/CsvOutput.cpp)

本次 ETW 被拒，所以「成功 FPS 精度」及「成功捕獲後 session 清理」仍需具備權限的環境驗證。應對照同一遊戲、同一時間區間的官方輸出，明確記錄 FPS 與 1% Low 定義。

驗收矩陣至少包括：DX11／DX12、視窗／全螢幕切換、程序退出、重新建立交換鏈、幀來源停止、權限拒絕、取消與重啟。成功與受限情境分別出具結果。

**4.3 強制終止時清理 PresentMon（P2）**

[PresentMonStream.cs](D:/Codex/Secondary/src/Secondary.App/Monitoring/PresentMonStream.cs:48) 正常取消會清理自己的 session；但父程序被強制終止時，finally 無法執行。硬體助手已有續租機制，PresentMon 缺乏對等的父程序存活約束。這是原始碼可見的缺口，本次沒有強制終止測試實際 session。

建議評估 Windows Job Object 的程序生命週期管理，並驗證它是否足以處理 ETW session；需要 session 回收時，以自己記錄的唯一 session 身分清理。也可用專用監督程序處理父程序失聯。所有停止操作應有整體 deadline，清理失敗須保留診斷。

驗收：在真正成功捕獲時終止父程序，檢查子程序與 ETW session 均結束；其他應用的捕獲不受影響。

**4.4 讓每項數據都有狀態、時間與來源（P2）**

目前 SystemSample 的 CPU／記憶體／網路沒有和硬體感測相同的新鮮度判定；Basic 失敗理由又寫入 gpuStatus，可能被下一次 GPU 採樣覆蓋。UI 也可能在來源失效時仍顯示 LIVE / HIGH 或 LIVE / LOW。

建議各來源採獨立狀態：等待基準、有效、過期、權限不足、已停止、重試中；保存最後成功時間與可讀原因。讓 UI 可以同時顯示「整機監測正常／FPS 權限不足」，而不是用一個 LIVE 標記概括所有來源。

驗收：分別令 CPU、GPU、助手及幀來源失敗，其他來源仍更新，失敗原因不被覆蓋，舊值明確變成過期或不可用。

[MainWindow.Game.cs](D:/Codex/Secondary/src/Secondary.App/MainWindow.Game.cs:117) 以硬體識別路徑及固定英文感測器名稱對應數值，GPU 選擇預設取排序後第一個。建議把廠商欄位及單位轉換集中成能力映射，明確分開 GPU 引擎負載、GPU Core 感測值、專用顯存與共享記憶體；記住使用者裝置選擇，保留顯式切換來源。

**5. 效能、資源占用與回應速度**

**5.1 優先量測並降低幀統計的配置量（P2）**

FrameWindow.Read 每次分組、排序、建立陣列；而 UI 每秒在 gameSession.Read 的共同鎖內執行此運算，可能短暫阻擋幀資料寫入。

Release 針對性量測，預熱後連續讀取 60 次：

| 保留幀數 | 最後一輪平均讀取時間 | 每次讀取配置量 |
|---|---:|---:|
| 3,600（約 60 FPS × 60 秒） | 0.660 ms | 139,688 bytes |
| 14,400（約 240 FPS × 60 秒） | 2.590 ms | 554,087 bytes |
| 60,000（容量上限） | 6.662 ms | 2,266,413 bytes |

其他重跑在 60,000 幀約為 5.6～7.3 ms。這是單一方法的本機微量測，不是整個應用的 CPU、峰值記憶體或記憶體洩漏證據。若每秒執行一次，容量上限案例約產生每分鐘 130 MiB 的短命物件配置，會增加 GC 工作。

建議共同鎖只負責資料交換，統計在背景產生不可變快照；分離最近 1 秒 FPS 與 60 秒 1% Low。以選擇最慢 1% 的方式取代完整排序，或在實測後選擇增量統計；表頭欄位索引也可一次解析後快取。

驗收：相同 fixture 的數值、亂序處理及容量保護一致；配置量有顯著下降；高幀率輸入下捕獲與 UI 不互相拖慢。

**5.2 恢復目前版本的效能量測（P2）**

[scripts/measure.ps1](D:/Codex/Secondary/scripts/measure.ps1:3) 直接 throw；[App.xaml.cs](D:/Codex/Secondary/src/Secondary.App/App.xaml.cs:17) 的 --measure 也顯示第一階段訊息並退出。[PerformanceRun.cs](D:/Codex/Secondary/src/Secondary.App/Monitoring/PerformanceRun.cs:40) 仍要求已不存在的 system 路由，因此單純移除停用訊息也不能取得有效新版報告。

建議以目前首頁／快捷／遊戲模式重寫情境，量測主程序加所有助手的總 CPU、Working Set、Private Bytes、配置量、handle／thread 數量及 UI 更新延遲；明確記錄 CPU 百分比的分母。

情境：靜態首頁、12 組件、圖片、影片、漸層、快捷 200 筆、遊戲高／低採樣、硬體助手開／關、隱藏及最小化。先取得可比較基線，再定資源預算；舊版預算不直接套用到所有新場景。

驗收：每份報告有版本、硬體、DPI、場景、有效採樣數、暖機時間與量測時間；隱藏後工作確實停止；長時間運行後資源不持續上升。

**5.3 將可能阻塞的工作移出 UI（P2）**

**10.4 保護既有包、驗證元件與簽章（P2）**

**10.5 評估發行包體積（P2／P3）**

目前本機 ZIP 約 153.4 MiB，解壓內容約 373 MiB。App 與助手各自自包含發布；比對兩個目錄，189 個檔案的 SHA-256 完全相同，重複那一份約 76.87 MiB。

這表示存在體積優化空間，不代表刪掉這些檔案即可正常執行，也不代表 ZIP 能等量縮小。可比較目前可攜式自包含包、需 runtime 的輕量包、安裝器共享 runtime，或經過驗證的統一部署布局。保留助手獨立程序和缺少 runtime 時的可用性；勿直接啟用 WPF trimming／單檔／ReadyToRun 後就假定相容與效能更好。
